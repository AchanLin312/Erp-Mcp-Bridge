
# Epicor-MCP-Bridge

**基于 Model Context Protocol (MCP) 的 Epicor ERP API 发现、调用与 Function 管理服务**

`Epicor-MCP-Bridge` 是一个 MCP Server，为 AI 编程助手（如 Cursor、Claude Desktop）提供 Epicor ERP 系统的完整操作能力。底层 HTTP 调用委托给 [EpicorRestAPI](https://www.nuget.org/packages/EpicorRestAPI/) 库处理（不自己造轮子封装 REST API）。

---

## 背景：Epicor 的两类可调用单元

| 类型 | 存储方式 | 管理方式 | MCP Tool 中调用 |
|---|---|---|---|
| **BO 方法** | 编译为 `*Contracts.BO.*.dll`，部署在 Assemblies 目录 | 通过 Swagger REST API 暴露 | 内部用 EpicorRestAPI 的 `BoPost` / `BoGet` |
| **EFX Function** | 数据库 `Ecf` Schema（`EfxFunction.Body` 存 C# 源码 JSON） | 通过 `EfxLibraryDesignerSvc` 的 BO 方法管理 | 内部用 EpicorRestAPI 的 `EfxCall` |

---

## 项目目标

让 AI 助手在本地协助 Epicor 二次开发时能够：

1. **发现**：知道有哪些 BO Service、每个 Service 有哪些方法、参数怎么填
2. **调用**：直接通过 MCP Tool 调用 BO 方法和 Function，用于测试和验证
3. **管理**：对 EFX Library 和 Function 进行增删改查、发布

典型工作流：AI 通过 MCP 测试 BO 方法了解行为 → 编写 Function 源码 → 通过 MCP 推送到 Epicor 服务器并发布 → 立即通过 MCP 测试该 Function。

---

## 核心特性

- **双模通信**：同时支持 `stdio`（本地直连）和 `HTTP/SSE`（团队远程共享）
- **极速服务发现**：扫描 Assemblies 目录下 `*Contracts.BO.*.dll` 文件名，毫秒级生成全部 BO Service 列表（当前环境有 6679 个 DLL）
- **按需 Schema 解析**：从 `swagger.json` 获取BO方法签名，递归解析 `$ref` 并过滤冗余字段，解决 Epicor Tableset 嵌套结构 300+ 字段导致的 Token 爆炸问题
- **统一调用入口**：`CallBoMethod` 和 `CallEfxFunction` 两个 Tool 统一处理 BO 方法和 Function 的调用，内部委托给 EpicorRestAPI
- **EFX Function 全生命周期管理**：基于 `EfxLibraryDesignerSvc`（28 个 BO 方法）实现 Library/Function 的 CRUD、发布、导入导出、锁定管理

## 工具设计原则

1. **MCP 是 AI 的唯一通道**：AI 不能直接调用 EpicorRestAPI，所有操作（发现、调用、管理）都通过 MCP Tool 暴露
2. **内部委托而非重复造轮**：`CallBoMethod` / `CallEfxFunction` 等执行类 Tool 内部用 EpicorRestAPI 完成 HTTP 请求，不自己封装
3. **按需解析**：不一次加载全部 Schema，AI 按需逐级获取
4. **Function 管理透明化**：MCP 封装 TrackChanges 流程（Get → Modify → ApplyChanges），用户只需提供 C# 代码
